# Apple × KRDS × 디자인 깎기 — 레퍼런스 선택 규칙

> 목표: 디자인 시스템을 '특정 외형을 복제하는 키트'가 아니라 **작업의 문제를 해결하는 비교 근거**로 활용한다. Universal Design v1.2 DRAFT에 자동 편입하지 않고, 별도 검토 뒤 v1.3 제안 시 근거로 사용한다.

## 1. 역할을 분리하자

| 설계 질문 | 1차 자료 | 2차 자료 | 피해야 할 오류 |
|---|---|---|---|
| 이용자가 첫 화면에서 무엇을 찾아야 하나? | KRDS 서비스 패턴·실제 사용자 과업 | Apple HIG Layout | 운영체제 스타일을 서비스의 성공 기준으로 취급 |
| 페이지 유형/콘텐츠 폭/좌우 정보 배치? | KRDS Layout + 기존 서비스 사례 | Apple macOS/태블릿의 구성 원리 | macOS 창 프레임/블러를 웹에 복제 |
| 모바일 최상위 이동/선택? | 이용자 IA, Apple iOS/iPadOS 탭/툴바 사례 | KRDS 내비게이션·패턴 | 하단 탭바가 없는 제품에도 무조건 도입 |
| 업무형 고밀도 목록·표? | KRDS 목록·필터·표, 실제 업무 요구 | macOS `Table Rows`·`Sidebars - Composed` | Apple 스타일을 적용했다고 웹 키보드/표 접근성이 확보됐다고 판단 |
| 모달·입력·오류·확인? | KRDS HTML 접근성 패턴, WCAG | Apple Sheet/Alert/Text Field | Apple 네이티브 접근성을 HTML에 자동 상속 |
| 색상·서체·브랜드·물성? | 해당 제품과 승인된 취향·콘텐츠 | Apple HIG Materials·Typography | 모든 서비스의 Liquid Glass화·SF 웹폰트 사용 |
| 동작·상태·모션? | 사용자 시나리오·상태 머신·회귀 계약 | Apple HIG 및 검증한 컴포넌트 | Figma 모양을 실제 작동·검증된 동작으로 간주 |

## 2. 설계 순서 — '스타일 선택'보다 앞에 둘 것

1. 프로젝트 목적과 주요 이용자/디바이스/과업을 기록한다.
2. KRDS 기본·서비스 패턴에서 적합한 페이지·업무 흐름을 찾아 **정보 구조**를 확정 후보로 정한다.
3. Apple의 **플랫폼 구조**(예: iPhone 탭, iPad 상단 툴바, macOS 사이드바·테이블)를 웹 UX에 전용할지 검토한다.
4. KRDS HTML 구조와 Apple 컴포넌트의 **역할만** 비교해 작업에 맞는 UI를 설계한다.
5. 제품의 브랜드·미적 취향을 **별도 단계**에서 반영한다. Apple 식 파란색/반투명 배경을 기본값으로 쓰지 않는다.
6. 실제 웹 환경에서 대비·키보드·터치·반응형·저장·복구·권한·기능 회귀를 테스트한다.

## 3. 추천 참고 예시 (도구 자체가 성능을 보증하지 않음)

**(A) 돌봄 플랫폼 — 환자·보호자 모바일**
- KRDS: [서비스 방문](../krds/PATTERN_ATLAS.md), [상세 정보](../krds/PATTERN_ATLAS.md)와 입력/오류/도움.
- Apple: `Tab Bar - iPhone`, `Row`, `Alert`의 역할/계층/현재 위치 표현.
- 사용자 접근성: 오늘 할 일·승인된 안내·연락처, 명확한 상태, 충분한 글씨, 인쇄 대안.
- **금지:** 의료적 검증 없이 자동 판정이나 확정 계획처럼 묘사하지 않음.

**(B) 돌봄 플랫폼 — 의료진 웹 워크벤치**
- KRDS: [목록 탐색·필터링·정렬·상세/입력](../krds/PATTERN_ATLAS.md).
- Apple: macOS `Sidebars - Composed`, `Table Rows`, `Sort Order Indicator`, `Popover`.
- 작업 맥락: A1 목록 → A2 근거 → A3 계획 초안, 승인/미승인 구분.
- **금지:** 네이티브 데스크톱 창 형태를 의무화하거나 임상 점수로 해석하는 것.

**(C) SAI 블로그**
- KRDS: 상세정보·목록·검색 패턴.
- Apple: 문맥에 맞는 `Search`, `Toolbar`, 콘텐츠/컨트롤 위계 원리.
- 콘텐츠: 학술 근거/해석 구분, 읽기·북마크·저장 상태.

**(D) MUL. 물컵 홍보**
- KRDS: 필요한 최소 탐색·접근성, 반응형.
- Apple: 소재 표현과 UI 조작층의 구분을 HIG Materials에서 연구.
- **금지:** Apple 폰트/아이콘/원본 Liquid Glass 요소를 일반 웹사이트에 직접 이전.

**(E) 메뉴 룰렛**
- 앱 자체의 단일 행동과 결과가 우선. Apple `Segmented Control` 등은 선택 입력의 참고만 하고, 슬롯머신 자체의 편집적 물성은 보존.

## 4. 혼합 전에 확인할 충돌

- Apple 플랫폼 관습 vs 웹에서 기대하는 탐색(뒤로가기, 주소, 키보드, 초점)
- KRDS의 한국어 레이블/오류 vs Apple 원본의 라벨·상태
- 마우스 hover vs 터치·키보드 동등 조작
- Apple 표면/폰트의 라이선스 vs 공개 웹 자산 정책
- 밀도 높은 의료진 화면 vs 환자용 쉬운 정보
- 단일 화면의 간결성 vs 상태/근거를 숨겨 발생하는 판단 위험
- 반응형 컨테이너에서 탭/사이드바 전환 시 데이터·필터·선택 상태 유실

## 5. Figma 최소 조회 프로토콜

1. `README.md` → 목적별 아틀라스 **하나만** 읽는다.
2. `component_catalog.json`에서 정확히 필요한 **1~3개 이름**을 고른다.
3. 내용이 미확인이면 `iOS and iPadOS 27` 또는 `macOS 27` **하나로 검색 범위를 좁혀** Figma를 읽는다. 검색 결과가 모호하면 근거 없는 variant를 쓰지 않는다.
4. 디자인 수준에서 필요한 값/상태/예제만 확인한다. **무료 계정 제약** 고려, 불필요한 전체 라이브러리 순회 금지.
5. 얻은 내용의 검증 범위·원본 버전·변경 날짜를 기록하고, 실제 제품 이식 시 라이선스를 재확인한다.

## 6. 범용 v1.3 개정 후보 (아직 미반영)

- **추가할 것:** 레퍼런스 선택의 단계별 규칙(문제→구조→상태→표현), Apple 플랫폼 특화/범용 원리 구분, 작업형 다중 정보 패턴.
- **반복하지 말 것:** 기존 v1.2의 폰트·색·접근성·저장·검증 계약 전체 본문.
- **별도 보존할 것:** 컴포넌트명/원본 접근 가이드/모달 유형/모션·질감 실험, Apple 전용 UI 리소스.
- **상태:** 편집 제안. 현재 v1.2 DRAFT를 개정하거나 사용자 승인된 프로젝트 코드를 변경하지 않는다.

## 검증

- **PASS:** Apple 공식 HIG의 기본 지침과 연결 Figma Apple 27 라이브러리 검색, KRDS 기존 허브의 패턴/컴포넌트 문서 비교.
- **NOT RUN:** 실제 라이브러리 전체 variants 확인, 네이티브↔웹 병렬 A/B/시각 테스트, 임상 사용자 테스트.
