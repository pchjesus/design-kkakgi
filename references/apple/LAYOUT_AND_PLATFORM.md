# Apple 레이아웃·플랫폼 패턴 아틀라스 v1.0

> **출처 분리:** (1) Apple 공식 HIG [Layout](https://developer.apple.com/design/human-interface-guidelines/layout)에서 확인한 일반 원리; (2) 연결된 iOS/iPadOS 27·macOS 27 Figma 라이브러리에서 **검색으로 존재만 확인한** 컴포넌트 이름; (3) 아래의 웹사이트 응용 후보(디자인 깎기 **가설**). Figma 캔버스의 실제 예제 화면을 세밀하게 시각 판독한 결과는 아니다.

## A. Apple HIG에서 확인한 레이아웃 원리

1. **과업과 콘텐츠가 우선:** 같은 화면에서 중요한 정보·조작이 시각적으로 식별되어야 한다. 계층은 정렬·근접성·여백·분리선·표면으로 구분한다.
2. **콘텐츠와 컨트롤은 계층을 구분:** 탐색/행동은 콘텐츠 위의 기능 레이어가 될 수 있다. Liquid Glass는 이 계층을 위한 시스템 표현이며 웹의 범용 유리 배경 제작법이 아니다.
3. **점진적 공개는 추가 콘텐츠의 존재를 알려야 함:** 숨긴 만큼 더 찾기 어려워지는 문제를 막는다. 자주 쓰는 기능까지 모두 팝오버에 넣지 않는다.
4. **유연한 화면:** 화면 폭·회전·크기 변경·텍스트 확대·현지화·입력 방식·시스템 안전 영역에서 구조를 조정한다.
5. **툴바와 탭바 역할 분리:** 툴바는 현재 화면에서 사용할 명령·검색·탐색을 담고, 탭바는 앱의 서로 다른 최상위 영역 사이 이동을 돕는다. 과업이 다른 두 기능을 같은 요소에 억지로 섞지 않는다.

## B. 플랫폼별 패턴 비교 — 관찰할 이름과 적합한 상황

| 설계 차원 | iOS/iPadOS 27에서 찾을 것 | macOS 27에서 찾을 것 | 웹 응용 가설 |
|---|---|---|---|
| 상위 화면 이동 | `Tab Bar - iPhone`, `Tab Bar - iPad` | `Sidebars - Composed`, `Outline View` | 소수 영역 이동 vs 깊은 계층 탐색 |
| 화면별 행동 | `Toolbar - Top - iPhone`, `Toolbar - Top - iPad` | `Examples/Windows/Unified Toolbar + Title` | 자주 쓰는 도구를 작업 맥락 가까이에 배치 |
| 다량 데이터 | `Row`, `Row with Swipe Actions` | `Table Rows`, `Sort Order Indicator`, `Column Header` | 줄단위 상세 탐색 vs 표 비교/정렬 |
| 부가 작업 | `Sheet - iPhone`, `Action Sheet` | `Popover`, `Utility Panel Tab Bar` | 보조 동작을 원래 작업의 맥락을 잃지 않게 제공 |
| 검색 진입 | `Sidebar Search Field`, `Accessory Bar - iPhone/Search` | `Search` | 검색이 핵심이면 숨기지 않고 결과 변경과 연결 |
| 좁은 화면 대응 | `Tab Bar - iPhone`, `Sheet - iPhone` | `Windows - Composed`, `Sidebars - Composed` | 고정 좌우 3단을 모바일까지 유지하지 않기 |

해당 표는 **두 플랫폼 모두 실제 컴포넌트명이 검색된 것**만 연결했다. 값과 화면 동작은 별도 실제 Figma/프로토타입 분석 대상이다.

## C. 디자인 깎기 파생 페이지 후보 — Apple 공식 템플릿명이 아님

| 후보 | 구성 | 우선 과업 | 실패 조건 |
|---|---|---|---|
| A1. 집중형 모바일 홈 | 짧은 핵심 요약 + 주요 행동 + 선택형 1차 이동 | 오늘의 행동·일정·긴급 문의 | 전체를 카드로 채워 1차 행동이 흐려짐 |
| A2. 다중 영역 탐색 | 작은 화면의 최상위 탭 ↔ 넓은 화면의 선택적 사이드바 | 자료실·설정·장기 탐색 | 탭 깊이를 무제한 확장, 화면 전환에 문맥 손실 |
| A3. 업무형 워크스페이스 | 사이드바 + 행/표·상태 표시 + 상세/편집 영역 | 목록 선별·비교·수정 | 장식·여백 과다로 실제 작업 정보가 줄어듦 |
| A4. 단일 도구형 | 명확한 오브젝트/조작부 + 결과 + 보조 도움 | 작은 반복형 도구·시뮬레이터 | macOS의 복잡한 윈도우 셸을 불필요하게 복제 |
| A5. 콘텐츠와 오버레이 | 본문 집중 + 맥락상 필요한 메뉴/시트/확인 | 읽기·선택·짧은 입력 | 중요한 정보가 항상 시트 속에 숨어 있음 |

**아키타입은 HIG 원문이 아닌 디자인 깎기의 기획 도구**로, 사용자는 적합하지 않으면 거절/변형할 수 있다.

## D. KRDS와 병렬로 참고하는 법

- **서비스 흐름·웹 정보 구조:** [KRDS 패턴 아틀라스](../krds/PATTERN_ATLAS.md)
- **PC/태블릿/모바일 페이지 폭·그리드:** [KRDS 레이아웃 아틀라스](../krds/LAYOUT_ATLAS.md)
- **앱 스타일의 컨트롤 계층·플랫폼 관습:** [Apple 컴포넌트 아틀라스](COMPONENT_ATLAS.md) 및 Apple HIG
- **실제 웹 구현:** 사용 중인 웹 프레임워크, 표준 시맨틱 HTML, WCAG/KWCAG, 프로젝트 데이터·상태 계약

**주의:** KRDS의 1200px 최대 콘텐츠 폭(표준형 예시)이나 Apple의 safe area를 웹 전체의 강제값으로 복사하지 않는다. 사용자 과업, 콘텐츠 폭, 반응형 목표에 따라 정당화한다.

## E. 사용성 검증 질문

1. 첫 화면에서 행동할 수 있는 대상과 읽어야 할 콘텐츠를 구별하는가?
2. 탭/사이드바로 바뀌었을 때 **같은 정보와 기능**에 접근할 수 있는가?
3. 팝오버/시트 뒤에서도 현재 환자·문서·필터·편집 중인 내용이 유지되는가?
4. 키보드/터치, 포커스 이동과 복귀, 화면 확대, 줄바꿈, 줄어든 움직임을 점검했는가?
5. 현재 플랫폼에 낯선 조작을 그대로 복제해 더 불편해지지는 않았는가?
6. 기존 업무 화면보다 클릭·스크롤·재탐색이 감소했는가? 실제 측정했다면 환경/방법 기록.

## 증거 상태

- **PASS:** HIG Layout/Toolbars의 일반 지침 읽기, 연결된 Figma 라이브러리에서 표에 등장하는 이름 확인.
- **NOT RUN:** Auto Layout·spacing 실제 값 추출, 개별 Figma variants 비교, iOS↔macOS 시각 렌더 비교, 웹 이식/사용성 테스트.
