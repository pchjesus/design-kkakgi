# Interactive Design & Creative Coding Playbook v0.1 — DRAFT

**범위:** 복잡한 모션·3D·인터랙티브 UI를 설계할 때만 선택적으로 적용. 보편 지침 v1.3 및 제품별 확정 계약보다 우선하지 않음. 2026-10-26 조사 기반.

## 1. Castle Jelly에서 추출할 원리 (원문 복제가 아닌 구조화)

| 레이어 | 원문에서 확인되는 사례 | 재사용 가능한 질문 |
|---|---|---|
| PURPOSE | 'material study' | 왜 상호작용을 만드는가? 학습·탐색·홍보 중 무엇인가? |
| ART DIRECTION | 종이 스튜디오, 파스텔성, 사탕 단면 | 구체적인 재질·빛·색·타이포·구도는 무엇인가? |
| SPATIAL MODEL | 호수, 성, 폭포, 배의 관계 | 객체의 배치·연결·가시성·카메라 규칙은? |
| INPUT | 터치/드래그, 다리·배·나무 조작 | 사용자는 무엇을 어떻게 입력하는가? 키보드·터치는? |
| RESPONSE | 파동 전파·수면 복원·불꽃놀이 | 즉시 피드백/시간적 진행/종료·취소·재진입은? |
| SIMULATION | 얕은물 파동·감쇠·고정 시간 물리 | 실제 검증된 모형인가, 시각적 근사인가? |
| CONTROL & RESPONSIVE | 우측 유리 제어판/모바일 하단 시트 | 정보를 어디에 표시하고 어떤 반응형 레이아웃이 필요한가? |
| ACCEPTANCE | 원문에는 상세 수락 테스트가 부족 | 실행·성능·fallback·접근성·시나리오별 검사 조건을 직접 명시해야 함 |

**주의:** 'WebGPU 한 파일', '외부 라이브러리 금지', '실시간 물리'는 특정 작품의 형식적 제약이다. 일반 프로젝트의 표준 스택으로 강제하지 않는다. 원문에 적힌 효과가 실제 물리적으로 검증됐다고 말하지 않는다.

## 2. 어떤 요청에서 어떤 경로로 갈까?
1. **국소 UI 수정:** 현행 v1.3 빠른 카드 → HTML/CSS/기존 스택. 새 라이브러리 불필요하면 추가 금지.
2. **짧은 모션·스텝 애니메이션:** CSS/WAAPI를 먼저 검토. 복잡한 타임라인·SVG/드래그가 필요할 때만 Anime.js 문서와 번들·호환성 확인.
3. **색상 방향 제안:** Coolors에서 후보 2~3개 생성 → 역할 토큰(primary/surface/text/state/outline) → 실제 밝고 어두운 배경 및 대비 확인 → 1안 선택.
4. **독창적인 실험형 페이지:** Codrops에서 실제 시연과 튜토리얼을 함께 제공하는 관련 사례 1~2개 조사 → 구조/기술 원리만 추출 → 기존 브랜드·자산·코드 복제 회피.
5. **3D/물리 시뮬레이터:** state/physics/render/input 4계층 분리, 검증된 실제 모델 vs 교육용 근사 vs 시각적 연출을 표기. Three.js/Canvas/WebGL/WebGPU는 현재 환경·유지보수·fallback 비교 후 선택.
6. **환자·보호자 의료 앱:** 모션 최소·명확한 동작 확인 우선. 건강 상태·의료 정보의 추정/승인/공개 범위를 애니메이션이 흐리게 만들지 않기.

## 3. 공통 명세 8칸 (복잡한 작업에만)
1. **GOAL:** 누구에게 무엇을 해주기 위한가 / 성공 기준
2. **CONTEXT:** 프로젝트 버전·현재 파일·보존할 기능·예산/기기
3. **CONTENT/SPACE:** 등장 객체·정보 구조·관계
4. **VISUAL:** 팔레트 역할·재질·타이포·광원·반응형 배치
5. **BEHAVIOR:** 사용자 입력 → 즉각 피드백 → 시간 경과 → 안정 상태
6. **STATE/EXCEPTION:** IDLE/ACTIVE/SETTLING/DISABLED/ERROR, 취소·중단·반복·초기화
7. **IMPLEMENTATION:** 기존 의존성 재사용, 새로운 기술 도입 근거, 성능 단계, fallback
8. **ACCEPTANCE:** 상태 전이·모바일·키보드·대비·reduced motion·성능·회귀·검증 상태

## 4. 상황별 짧은 지시문

### A — 아이디어/디자인만 탐색 (코드 수정 X)
```text
대상: [프로젝트/화면].
목표 사용자와 행동: [누가/무엇].
Codrops/기존 레퍼런스 1~2개에서 겉모양이 아니라 레이아웃·움직임·상태 피드백의 원리를 추출해라.
다른 방향의 시안 2개를 비교하고, 기존 UX/브랜드/상태를 보존할 수 있는 제안을 해라.
결과는 관찰 근거·적합/부적합 상황·시각화 가설·검증 방법으로 나눠라. 코드는 변경하지 마라.
```

### B — 색상 개선
```text
기존 컬러 역할 토큰과 실제 화면 대비를 먼저 확인해라.
Coolors 후보는 참고만 하고, 배경·표면·텍스트·강조·오류/성공의 역할을 분리한 2안을 제시해라.
작은 텍스트/비활성/상태 정보의 대비와 밝은/어두운 환경을 점검하고 색상만으로 상태를 표현하지 마라.
승인 전 브랜드 전체 교체·배포는 하지 마라.
```

### C — 마이크로인터랙션 구현
```text
현재 동작과 관련 코드를 먼저 좁혀 확인해라.
[조작]에서 [반응]까지의 상태 전이를 정의하고, 입력 중단·빠른 연타·중복 실행·초기화를 포함해라.
CSS/WAAPI로 충분하면 Anime.js를 추가하지 말고, 타임라인·SVG·드래그 등이 필요하면 도입 비용을 비교해라.
키보드/터치/포커스/동작 감소 설정과 기존 기능·저장·성능 회귀를 확인해라.
변경 파일, 선택 이유, PASS/FAIL/NOT RUN을 보고해라.
```

### D — 3D/시뮬레이터 구현
```text
이 프로젝트의 목적은 [교육/시각적 실험/실제 물리 근사]이다.
등장 객체·카메라·재질·광원·제어판·모바일 배치를 명시하고, 사용자 입력 → 객체 반응 → 감쇠/복원 과정을 설계해라.
물리/생리 계산·렌더링·UI 상태를 분리하고 정확도·근사 범위를 명시해라.
기존 동작과 배포 구성을 보존하고, WebGL/WebGPU 호환성 및 fallback을 검토해라.
단계적으로 MVP → 상호작용 → 시각 품질 → 성능/접근성 → 회귀 검증을 진행해라.
실행 테스트하지 않은 항목은 PASS라고 하지 마라.
```

### E — 기존 작품 고도화 (보수적 패치)
```text
기존에 사용자가 승인한 요소·GitHub 공개 경로·저장 형식은 고정한다.
변경 대상 파일만 조사하고, 요청한 [문제]만 수정한다.
회귀 위험/예외 상태/성능을 확인한 뒤 영향 범위에 비례해 검증한다.
무관한 리팩터링, 디자인 재해석, 라이브러리 교체, 배포는 하지 마라.
```

## 5. 객관적 검사 (선택형 체크리스트)
| 범주 | 최소 관찰 |
|---|---|
| 행동 | 클릭/드래그/연타/중단/취소/복귀/초기화, 중복 이벤트 |
| 상태 | 시작·진행·완료·실패·비활성 표시, 화면 전환 뒤 상태 |
| 접근성 | 키보드/초점, 터치 대체 입력, 화면 읽기, reduced motion, 텍스트/컨트롤 대비 |
| 반응형 | PC/모바일 제어판, 한 손 조작, 화면 확대, 가로/세로 회전 |
| 성능 | 목표 기기에서 실제 측정, 해상도/효과 단계 조정, 프레임 저하·메모리 누수 |
| 정확도 | 시각적 근사와 정량적·의학적 정확도 증거 구분 |
| 회귀 | URL·저장/복원·기존 기능·에러 처리·공개 상태 |
| 보고 | 각 항목 PASS / FAIL / NOT RUN / N/A 및 테스트 환경 |

**접근성 참고:** WCAG 2.2의 일반 텍스트 대비 기준 4.5:1(큰 글자 3:1), 필수 UI 시각 요소 대비 3:1은 해당 기준 적용 조건을 정확히 판단해야 한다. 배경 색 조화 자체는 합격 근거가 아니다.
