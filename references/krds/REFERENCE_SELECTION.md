# 디자인 레퍼런스 선택 프로토콜 v1.0

**목적:** '한 종류의 화면만 반복 생성'하는 습관을 줄이고, 과업에 맞는 **정보구조 → 레이아웃 → 컴포넌트 → 시각 표현**의 선택지를 체계적으로 생성·검증한다. 레퍼런스는 **증거/비교재**이지 복제 대상이나 자동 승격되는 디자인 규칙이 아니다.

## 0. AI 작업 진입점 — 필요한 파일만 검색

- **화면 전체/레이아웃 문제** → [LAYOUT_ATLAS](LAYOUT_ATLAS.md) (웹 공식 출처)
- **사용자 행동·페이지 흐름** → [PATTERN_ATLAS](PATTERN_ATLAS.md) → 정확한 공식 링크가 필요한 경우 [pattern_catalog.json](pattern_catalog.json)
- **개별 UI/동작** → [COMPONENT_GUIDE](COMPONENT_GUIDE.md) → [component_catalog.json](component_catalog.json)
- **색/텍스트/간격** → [TOKEN_GUIDE](TOKEN_GUIDE.md)
- **실제 코드 반영** → [INTEGRATION_AND_QA](INTEGRATION_AND_QA.md)
- **원본 버전/신뢰도** → [SOURCE_PROVENANCE](SOURCE_PROVENANCE.md)
- **개인 선호·시각적 미감** → 디자인 깎기의 기존 `references/` 취향 지도 및 프로젝트 피드백. KRDS를 취향의 대체물로 쓰지 않는다.

## 1. 레퍼런스 역할 분담

| 참고 체계 | 우선 검토 분야 | 적용 범위/주의 |
|---|---|---|
| **KRDS** | 한국어 정보 구조, 공공성 높은 서비스, 복잡한 폼·여정, 반응형 레이아웃, 상태·접근성 | 공공서비스 문맥의 권고를 다른 산업에 자동 강제하지 않음 |
| **Apple HIG·UI Kit** | 앱의 화면 계층, 플랫폼 관습, 내비게이션·컨트롤 일관성, 사용성·동작 상태 | iOS/macOS 고유 패턴을 웹에 무비판적으로 복제하지 않음. Apple 원본 Figma 파일은 아직 분석/등록하지 않음 |
| **NHS** | 의료·건강 정보 제공, 쉬운 표현, 안전성과 과업 흐름 | 임상적 근거/개별 환자 안전을 자동 보장하지 않음 |
| **IBM Carbon** | 업무 대시보드, 구조화 데이터, 상태, 밀도, 디자인 토큰 | 전문 도구에 유리하나 홍보 사이트에 그대로 적용할 이유는 없음 |
| **사용자 확인 레퍼런스** | 브랜드 적합성, 타이포그래피, 색상, 물성, 리듬, 이미지 표현 | 확인한 **좋아하는 요소만** 기록; 범용 정답/접근성 증거와 구분 |
| **WCAG/KWCAG** | 지각·조작·이해·호환성의 검증 기준 | 공식 디자인 킷의 외형만으로 인증 불가 |

※ 표의 Apple/NHS/Carbon 정보는 기존 범용 지침과 각각의 디자인 시스템 용도를 바탕으로 한 **선택 원칙**이다. 이 문서는 KRDS 외의 타 시스템을 새로 수집·검증한 기록이 아니다.

## 2. 작업 전 질문 → 가능한 레이아웃 최소 2안

요구 파악: **이용자 / 핵심 행동 / 정보 밀도 / 탐색 깊이 / 기기 / 사용 빈도 / 접근성 / 브랜드 성격 / 기존 기능 / 미검증 가정**.

- **안 A: 정보·작업 효율형** — 중요 항목과 빈번한 행동이 우선. 비교가 핵심이면 표, 복잡한 IA면 선택적 내비게이션.
- **안 B: 탐색·설명 중심형** — 단계적 정보 공개, 요약과 구조화된 본문, 적절한 콘텐츠 리듬.
- **안 C(유의미할 때만): 시각 탐색형** — 이미지·시각 자료가 내용의 일부인 제품/전시/홍보. 동등한 정보 접근 경로 유지.

후보마다 **가설 → 장점 → 실패 조건 → 모바일 대안 → 근거 출처 → 미검증 항목**을 1행씩 남긴다. 공간만을 채우려고 패널·카드·3D·모션을 추가하지 않는다. 사용자 또는 대상 제품 계약이 이미 충분히 구체적이면 억지로 3개를 생성하지 않는다.

## 3. 채택 판단표

| 평가축 | 질문 | 검증 방법 |
|---|---|---|
| 과업 적합성 | 중요한 행동을 찾고 성공적으로 마칠 수 있나? | 단계/클릭 수 및 시나리오 |
| 정보 위계 | 무엇이 첫 번째·두 번째·세 번째로 보이나? | 실제 화면 비교/사용자 테스트 |
| 가독성/밀도 | 화면 폭을 과소·과대 활용하지 않나? | 320/390/768/1024/1440px 점검 |
| 시각 맥락 | 타이포·색·물성이 콘텐츠·서비스 성격과 맞나? | 사용자 피드백/레퍼런스 대조 |
| 접근성 | 키보드·초점·명도·읽기 순서·오류 복구가 적절한가? | WCAG/KWCAG 항목별 |
| 기능·회귀 | 저장·복원·탐색·모달·권한·상태가 유지되는가? | 기존 기능 계약과 비교 |
| 구현 비용 | 패키지 의존성/장기 유지 비용은? | 변경 파일, 의존성, 번들 검사 |

**결정 기록:** 적용 / 부분 채택 / 거절 / 미검증으로 구분. '예쁜 디자인'이라는 단일 근거로 승인하지 않는다.

## 4. 합성 시 주의사항

- 레퍼런스의 **구조**를 읽는 것과 **시각 자산**을 복제하는 것은 다르다.
- 서로 다른 시스템의 컨트롤을 섞으면 focus/hover/disabled/간격 토큰/모션/ARIA 상태의 정합성을 확인한다.
- KRDS나 Apple을 참고해도 **사용자 승인된 기능·브랜드·UX 계약이 먼저**다.
- 참고 자료가 모자라면 공식 출처/필요한 화면을 더 읽되, 모든 컴포넌트 원본을 통째로 로드하지 않는다.
- 추론으로 만든 레이아웃 후보를 'KRDS 공식 템플릿'이라고 표기하지 않는다.

## 5. Apple 공식 Figma 파일이 나중에 제공될 경우

- 별도 `references/apple/`로 분리해 **플랫폼·버전·출처·라이선스·확인 범위**를 먼저 기록한다.
- **최적 입력:** Figma 파일에 접근 가능한 공유 링크(권한 필요할 수 있음) 또는 `.fig` 원본 + 주요 페이지 프레임의 PDF/PNG/SVG 내보내기. .fig 단독은 환경에 따라 전체 구조를 직접 해석할 수 없으므로 **검증 범위를 보수적으로 표시**.
- 가능하면 **컴포넌트명 / variants(상태) / auto layout / spacing / 색·타이포 스타일 / 화면 예시**를 분리해 구조화한다.
- 컴포넌트/스타일 수는 검증 가능한 범위만 세고, 빠진 레이어를 임의로 보완하지 않는다.
- SF Symbols, SF Pro 등의 폰트·아이콘과 Apple 원본 프레임을 허가 없이 Public GitHub에 복제하지 않는다. Apple 리소스 사용은 제공 라이선스 조건을 우선 확인한다.
- Figma 원본 자체를 참조하더라도 웹에서의 적용은 Apple의 플랫폼 관습과 사용자의 사이트 목적을 구분한다.
- 해당 파일을 받기 전에는 원본 디자인을 **분석 완료/등록 완료**라고 표기하지 않는다.
