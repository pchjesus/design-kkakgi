# Universal Visual Design & UI/UX Guidelines v1.3 — Modular Edition

> **상태:** **DRAFT / 사용자 검토용 / 미승인** · 2026-10-20
>
> **기준:** [v1.2 DRAFT 원본](Universal_Visual_Design_UI_UX_Guidelines_v1.2.md) 보존. 범용 UI/UX 지침을 **핵심 결정 기준 + 선택적 참조 모듈**로 재구성한다. 특정 도구의 구현·공식 임상 성능·브랜드 정체성을 승인하거나 바꾸지 않는다.
>
> **적용:** 웹·모바일 앱, 사이트, 블로그, 업무/대시보드, 교육·시뮬레이터, 정보 시각화, 문서·발표. 시뮬레이터의 생리 모델·상태 엔진은 별도 전문 계약을 우선한다.

## 0. 읽는 법 — 이 문서를 매번 전부 읽지 않는다

### 0.1 규범과 출처의 구분

- **MUST:** 이해 가능성, 사실성·정직성, 접근성, 안전, 상태·데이터·기존 승인 계약에 관계되는 필수 조건. 예외는 해당 프로젝트/규정의 근거·승인을 기록.
- **SHOULD:** 많은 과업에서 유리한 출발점이나 실제 상황/검증에 따라 조절할 설계 권고.
- **MAY:** 특정 프로젝트에 적합하면 선택하는 형태·색·모션·토큰 예시.
- **증거:** `[STANDARD]` 공식 가이드/규범, `[IMPLEMENTED]` 구현 확인, `[USER]` 직접 선호, `[OBS]` 관찰, `[HYPOTHESIS]` 다른 맥락 적용 가설, `[NOT RUN]` 미검증. **서로 대체하지 않는다.**
- **권한:** 사용자/프로젝트에서 승인된 UX·기능·데이터 계약·브랜딩 및 의료·법적 안전 요구가 범용 디자인 권고보다 우선한다. 지침 신규 버전은 기존 앱이나 타 프로젝트를 자동 변경하지 않는다.

## 1. 핵심 철학 — 목적에 따른 디자인

디자인은 **의미·정보 구조·조작·신뢰·표현적 정체성**의 설계다. 디터 람스/Braun의 'Less, but better'는 내용과 필수 기능을 버리라는 뜻이 아니다. 실제 제품의 원리를 디지털에 옮길 때는 동작·정렬·비례·절제의 **목적**을 검토하고 외형/저작물을 베끼지 않는다. [v1.2의 Rams/Braun·ChatGPT·Apple 상세 관찰](Universal_Visual_Design_UI_UX_Guidelines_v1.2.md)은 중복하지 않고 참조한다.

### 1.1 지켜야 할 8개의 기준

1. **목적 우선:** 무엇을, 누가, 어디에서, 왜, 얼마나 자주 사용하는지 먼저 정의한다.
2. **정보 위계:** 중요한 내용과 행동은 빨리 발견되고, 함께 판단할 정보는 연결돼 있어야 한다.
3. **역할·상태의 정직성:** 실제 권한·진행·승인·출처·불확실성·예시/시연 여부를 표현이 왜곡하지 않아야 한다.
4. **맥락에 맞는 정보 밀도:** 미니 도구는 집중, 전문가 업무는 비교, 학습·홍보는 탐색을 지원. 한 가지 정렬·카드·여백 스타일을 기본 정답으로 취급하지 않는다.
5. **실제 상호작용:** 가능한 행동, 현재 선택, 처리 중·오류·복구·취소/되돌리기를 명확하게 드러낸다.
6. **접근성과 다양한 환경:** 키보드·터치·확대·축소 모션·읽기 순서·언어·반응형을 초기부터 검토한다.
7. **표현의 맥락 적합성:** 타이포·색·물성·모션을 브랜드와 콘텐츠에 맞게 고르며, 시각적 절제와 개성을 이분법으로 보지 않는다.
8. **검증 가능한 개선:** 선호 평가와 객관적 과업 성공, 코드·브라우저 테스트를 분리. 새 버전이 항상 개선판이라고 가정하지 않는다.

## 2. 설계 순서 — 기능 흐름 → 구조 → 표현

### 2.1 요구와 보존할 강점 정의

- **이용자·역할:** 사용자·담당자·관리자 등 누가 같은 데이터에서 **어떤 정보와 권한**을 볼 수 있는지 구분한다.
- **JTBD:** 주요 성공 행동 1개 + 자주 필요한 보조 행동. 홍보는 감상/브랜드 이해가 주요 성과일 수 있고, 업무 도구는 빠른 정보 비교가 성과일 수 있다.
- **콘텐츠 계약:** 정보 출처·시점·결측·확정 상태·설명/행동의 경계와 필수 정보를 정리한다.
- **기존 프로젝트:** 작동하는 기능, 데이터·URL·저장 상태, 사용자 승인된 미감/배치 등 **바꾸지 말아야 할 강점**을 명시한다.
- **새 프로젝트:** 정보가 없으면 근거 없는 기능/실환자 데이터/가짜 수치를 만들지 않는다. 필요한 경우 **가상·시연**을 명확히 표시한다.

### 2.2 페이지 구조/작업 상태를 시각 디자인보다 먼저

**SHOULD:** 신규 사이트/큰 개편에서 1차 작업에 맞는 **서로 유의미하게 다른 2안**을 비교한다. 예: 화면 넓게 쓰는 2열+요약 vs 중앙 집중 단일 도구, 카드 요약 vs 비교용 표, 상위 탭 vs 좌측 탐색. 국소 패치에는 강제하지 않는다.

| 정보/작업 목적 | 우선 후보 | 실패 신호 |
|---|---|---|
| 방문·발견 | 사용자 목적별 진입, 명확한 제목/가치, 필요한 경우 콘텐츠 허브 | 장식 히어로·감성 카피가 작업을 밀어냄 |
| 목록 선별·비교 | 검색·필터·정렬·표/리스트·선택 상태 | 모든 값을 고립된 카드에 넣어 비교 불가 |
| 상세 설명·읽기 | 요약→근거/본문→관련 행동, 필요 시 본문 목차 | 출처/조건/변경 시점을 숨김 |
| 다단계 입력·처리 | 작업 단계·입력·검증·검토·결과를 구분 | 단계가 바뀌면 환자/항목/임시 입력이 유실 |
| 작은 단일 도구 | 오브젝트/핵심 조작/결과 중심의 집중 레이아웃 | 넓은 화면을 채우려 불필요한 양측 패널 생성 |
| 고밀도 업무 | 목록/세부/작업 영역의 필요 시 동시 노출 | 정보를 과잉 압축하거나 의미 없는 공백으로 분산 |

**참고:** [KRDS 패턴](../../../references/krds/PATTERN_ATLAS.md) / [Apple 플랫폼 아틀라스](../../../references/apple/LAYOUT_AND_PLATFORM.md) / [Material 3](../../../references/material3/README.md). 어떤 시스템도 자동 채택하지 않는다.

### 2.3 역할별 정보 밀도와 맥락 보존

- **MUST:** 다른 역할의 화면을 단지 크기만 바꿔 재사용하거나 **내부 데이터/미승인 항목을 다른 역할에게 그대로 공개하지 않는다.** 실제 계정 인증·인가/데이터 권한은 UI 모양만으로 해결되지 않는다.
- **SHOULD:** 전문 작업자는 **비교 가능한 병렬 정보·빠른 편집·결측·근거**를, 처음 이용하는 일반 사용자는 **오늘 할 행동·시간·다음 단계·문의처** 같은 목표 중심 내용을 우선할 수 있다. 실제 대상자 조사로 검증한다.
- **SHOULD:** 정보 밀도가 높다고 무조건 섹션을 접지 않는다. **동시에 판단할 정보는 나란히**, 부차적 설명·희귀 옵션만 점진적으로 공개한다.
- **MUST:** 진행/결과/승인/발행을 실제 데이터 상태와 연결한다. **미평가 ≠ 정상·0, 초안 ≠ 승인, 처리 시작 ≠ 완료, 사용자 체크 ≠ 임상적 수행 인증**. 도메인 고유 예시는 범용 규칙이 아니다.
- **고위험 상황:** 임상적 위험도·행정 자격·공식 결정처럼 특수한 판단은 **공식 규칙과 자체 모델, 사용자 메모, AI 생성 가설을 구분**하고 검증되지 않은 점수를 공적 판정처럼 제시하지 않는다.
- **근거:** [환자 우선 제품 PRD](https://github.com/pchjesus/ai-care-transition-platform/blob/main/docs/PATIENT_FIRST_MVP_PRD_DRAFT_v0.2.md)와 [병원 흐름](https://github.com/pchjesus/ai-care-transition-platform/blob/main/docs/MVP_WORKFLOW_AND_DATA_CONTRACT_DRAFT_v0.2.md)은 **기획·목업 단계**, 의료기관/사용자 실증 아님.

## 3. 공간과 정보 표현

### 3.1 레이아웃·반응형

- **SHOULD:** 먼저 정렬축·컨테이너 폭·열 비율·간격·그룹을 정의한다. 탐색·선택 영역과 내용을 읽거나 편집하는 영역은 **각각의 정보량과 사용 빈도에 따라 유효 폭을 다르게 배정**할 수 있다. 패딩·행 길이·실제 줄바꿈까지 확인하며, 1:1·1:2 같은 비율을 전역 정답으로 고정하지 않는다.
- **SHOULD:** 전체 폭 확대가 모든 문제의 해결책은 아니다. [MUL. E8](../../../cases/mul-cup/DESIGN_LEARNINGS_E7_E8.md)은 우측 유효 폭 확대가 유리했고, [메뉴 룰렛](../../../cases/menu-roulette/LESSONS.md)은 중앙 집중이 유리했다. **각각의 사용자 평가일 뿐 범용 성능 증거는 아니다.**
- **MAY:** 간격 출발점 `4/8/12/16/24/32/48/64px`. KRDS의 표준형 콘텐츠 1200px, Apple safe area, M3의 레일 등의 수치는 **각 체계/플랫폼의 맥락 값**이지 전역 불변값이 아니다.
- **MUST:** 좁은 폭/확대에서 중요한 정보·기능을 유지. 표·지도처럼 본질적으로 2차원인 부분은 필요한 가로 스크롤을 명시하고 나머지 레이아웃은 논리적으로 재배치한다.
- **SHOULD:** 콘텐츠의 정렬/폭을 손보기 전에 불필요한 카드/패널부터 추가하지 않는다. 컴포넌트 외곽 테두리를 줄이더라도 실제 클릭 영역·초점·상태 식별은 보존한다.

### 3.2 타이포그래피와 카피

- **MUST:** 한국어와 영문·숫자·기호 혼용 시 실제 렌더링/폴백·줄바꿈, 필수 정보의 읽기 위계를 점검. 영문 이탤릭을 한글 제목에 적용하는 과정에서 글리프 폴백이나 합성 이탤릭 문제가 없는지 확인.
- **SHOULD:** 폰트 선택은 크기·굵기와 별개로 **소재·목적에 맞는 서체의 형태와 리듬**을 기준으로 결정한다. 브랜드명이 로고·헤드라인 등 여러 위치에 반복되면 **서체 관계의 일관성**을 확인한다. 제목의 의도적 행 나눔은 의미와 시각적 무게를 고려해 유지할 수 있으나, 좁은 폭의 우발적 줄바꿈·넘침과 구분하여 실제 렌더링을 점검한다. 웹 장문은 약 16px 이상, 보조 설명은 가급적 14px 이상, 본문 행간 약 1.5~1.7에서 검토한다(고정 규격 아님).
- **SHOULD:** 역할 기반 타이포그래피 토큰(`display/title/body/caption/data`)과 실제 한글 폴백·라이선스를 설정. 지나치게 큰 히어로·영어 overline·모호한 감성 슬로건을 관성적으로 반복하지 않는다.
- **MUST:** 통계·의료·과학/AI 콘텐츠에서 사실·가정·시연·해석·한계·출처를 혼동시키는 카피를 만들지 않는다.

### 3.3 색상·표면·이미지

- **SHOULD:** 색채 방향은 **브랜드·실제 소재의 성질과 연상, 빛·사용 환경, 정보 밀도**에 근거해 고른다. 장식색과 상태 의미색(`surface/text/accent/success/warning/danger/focus`)을 구분하고, **어떤 정보 영역에 시선이 집중되는지 실제 화면에서 확인**한다. 자연광 계열이나 녹색 등 특정 연상색, 크림·회녹색 같은 익숙한 팔레트를 업종별 정답으로 고정하지 않는다.
- **MUST:** 색만으로 필수 상태를 구별하지 않는다. 대비와 비텍스트 구별, 실제 이미지 위 텍스트를 확인한다. 명료성 때문에 필요하면 표현적 색채도 제한한다.
- **SHOULD:** 물성 표현은 **실제 제품 오브젝트**와 **UI 조작/내비게이션 레이어**를 구분. Apple Liquid Glass 등은 목적이 맞을 때만 원리 참고; 모든 콘텐츠 카드의 유리화는 하지 않는다. Apple 원본 에셋/SF 폰트 등의 배포에는 별도 라이선스 제약이 있다.
- **SHOULD:** 질감 강도·표면의 미세 결·광택·빛·그림자·구도의 역할을 별도로 조절. 과한 질감을 줄였다는 사용자의 피드백을 '어떤 재질이든 얇게'라는 범용 법칙으로 승격하지 않는다.
- **MUST:** 외부 이미지/저작물의 권리·출처를 확인하고, 실제 없는 사진·실제 기관의 협력/검증 결과처럼 보이게 하지 않는다.

### 3.4 모션·인터랙션의 물리성

- **SHOULD:** 모션 목적을 **피드백 / 상태 전환 / 공간적 인과 / 직접 조작 / 브랜드 분위기** 중 무엇인지 명시. 동시다발적 페이드·회전/스크롤 강제는 기본값이 아니다.
- **SHOULD:** 물체의 재질과 움직임을 연관 짓는다. 예컨대 유리 제품은 비강체처럼 늘어나는 반동보다 **접촉·가속·반사/그림자**의 연계가 어울릴 수 있음. 구체적 선호는 [MUL. E8 사례](../../../cases/mul-cup/DESIGN_LEARNINGS_E7_E8.md) 수준이며 일반 물리 법칙은 아님.
- **MUST:** 직접 조작을 방해하거나 현재 상태를 알아보기 어렵게 만드는 모션을 피한다. `prefers-reduced-motion` 및 접근성 대안을 고려하고 모션 없이는 핵심 의미가 사라지지 않게 한다.
- **MUST:** 3D/Canvas 등은 **실제 브라우저 출력·성능·대체 입력**을 점검. 모델의 기술적 회전 가능과 표면의 미적 완성, 안전성/사용성을 서로 다른 검증으로 기록한다.

## 4. 상태·접근성·콘텐츠의 안전한 전달

### 4.1 상태와 검토 주체

| 상태 층위 | 사용자가 알아야 할 것 | 잘못된 표시의 예 |
|---|---|---|
| 편집 | 저장 전/임시/저장됨·마지막 시각 | 저장 확인 없이 '완료' |
| 검토 | 미확인/결측/상충/검토 대기/검토 완료 | 결측을 정상으로 자동 채움 |
| 승인·공개 | 누가 승인했고 어떤 버전이 공개됐는가 | 작성 초안을 외부에 바로 공개 |
| 외부 처리 | 요청/접수/수락/제공/종결 등 **해당 서비스의 실제 단계** | 수락을 서비스 제공 완료라고 표시 |
| 오류·복구 | 무엇이 실패했고 다시 할 수 있는가 | 빨간 아이콘만 보이고 복구 불가 |

**MUST:** 상태 명칭과 권한은 제품별 실제 상태 머신/전문 규칙을 따른다. 위 표의 예시가 모든 제품의 필수 데이터 모델은 아니다. 로그인 UI를 만들었다고 인증·인가·감사 로그를 구현한 것으로 주장하지 않는다.

### 4.2 최소 접근성 계약

- **MUST:** 시맨틱 제목·레이블·인접 설명, 키보드와 논리적 초점/복귀, 현재 위치·선택 상태, 오류 메시지, 읽기 순서, 적정 hit area와 대체 조작.
- **MUST:** 최신 해당 프로젝트 적용 접근성 기준을 확인. WCAG 2.2 AA를 목표로 할 때 일반 텍스트 대비 **4.5:1**, 큰 텍스트 **3:1**, 정보성 비텍스트 컨트롤 경계/상태 **3:1**(적용 예외 확인). 숫자만으로 전체 접근성 충족을 주장하지 않는다.
- **MUST:** 텍스트 200% 확대(SC 1.4.4)와 **320 CSS px 상당 리플로우**(SC 1.4.10)는 별개로 테스트. 한글·영문 혼합과 긴 URL/DOI의 실제 줄바꿈을 본다.
- **SHOULD:** 의료·고령·소수 숙련 사용자를 위해 설명의 쉬운 표현·충분한 터치 크기·인쇄/대체 경로·도움/문의처를 테스트하되 **유아용으로 보이는 과장된 UI나 과도한 공백을 자동 강제하지 않는다**.
- **MUST:** 실제로 보조기기/실기기를 쓰지 않았다면 접근성 인증·모바일 실측 `PASS`로 기록하지 않는다.

## 5. 디자인 시스템·토큰 적용 원칙

- **KRDS:** 웹페이지·한국어 입력·기본/서비스 패턴·반응형 정보 구조를 먼저 참고. [공식 레이아웃과 선택적 HTML 컴포넌트 탐색](../../../references/krds/README.md).
- **Apple HIG / Figma:** 모바일·태블릿·데스크톱의 컨트롤/탐색 위계, 네이티브 플랫폼 관습과 디테일을 참고. [연결 라이브러리의 **일부 컴포넌트명 95개**](../../../references/apple/README.md)만 확인, 전체 Figma UI Kit 수/variants/토큰과 공식 동일성은 검증 전.
- **Material 3:** [연결 Community Kit의 **선별 컴포넌트 검색**](../../../references/material3/README.md)과 Google 공식 adaptive/navigation 문서를 참고. M3 Expressive처럼 버전 변경 가능성이 있는 패턴은 최신성을 확인한다. **색/간격/변형 값 직접 추출·전수 분석은 미실시**.
- **Rams·ChatGPT 등:** 고전 제품의 질서·물리적 조작 원리, 현대 읽기 인터페이스의 집중/입력 UX를 맥락별로 참조. 외형/로고/브랜딩 복제 금지.
- **토큰:** `color(surface/text/accent/status/focus)` · `type(display/body/data)` · `space` · `radius` · `state(default/active/focus/busy/error)` · `motion(normal/reduced)` 같은 **역할 이름**만 공통 언어로 정의하고, 실제 색값·px·구성은 프로젝트별로 결정한다.
- **충돌 해결:** 각 시스템에서 **하나의 좋은 아이디어/문제 해결 원리**를 가져와 현행 제품의 토큰·브랜드·접근성에 맞춰 재해석한다. 다른 시스템의 표면·서체·컴포넌트를 섞을 때는 focus, density, hit area, motion, ARIA, state를 검증한다.
- **선택 지도:** [KRDS × Apple × Material 3 × 돌봄 서비스](../../../references/DESIGN_SYSTEM_SELECTION.md)를 참고. 자료를 많이 읽을수록 디자인이 좋아진다는 가정은 금지한다.

## 6. 구현·변경 위험·검증 계약 — 삭제하지 않는 핵심 MUST

### 6.1 작업 순서

1. **현행 기준 확인:** 대상 README·SPEC·AGENTS·DEVLOG·기본 브랜치·최신 코드, 기기/매체/사용자/상태 계약을 확인한다.
2. **진단:** 기존의 강점/사용자 문제·원인 후보를 분리한다. 색·폰트·레이아웃을 동시 변경하면 무엇 때문에 평가가 달라졌는지 확정하기 어렵다.
3. **대안:** 중요 변경에서 의미 있게 다른 대안 2안 정도와 **장점·실패 조건·유지 비용**을 비교. 기존 승인된 요소는 보존 목록에 넣는다.
4. **위험/상태 영향:** 정상·빈·오류·로딩·권한·저장·URL/내비게이션·모바일·고위험 정보/상태 전환에 영향을 주는지 검토.
5. **제한적 구현:** 승인된 범위에서만 변경, 기존 기능 보존·되돌릴 수 있는 구조 확보.
6. **검증:** 실제 화면과 동작, 저장/복원, 접근성, 버전 호환 및 영향받는 회귀를 테스트.
7. **기록:** 무엇을 채택/거절했고 **어느 환경에서 무엇을 실제로 확인했는지** 남긴다.

### 6.2 위험도와 최소 테스트

| 등급 | 예시 | 최소 점검 |
|---|---|---|
| **L 낮음** | 색·간격·문구·작은 장식 | 해당 화면 실제 렌더/대비·반응형/포커스 및 인접 영역 |
| **M 중간** | 컴포넌트·폼·필터·레이아웃·화면 이동 | 정상/빈/오류/연속 조작, 키보드·모바일, 선택·데이터 상태와 영향 범위 회귀 |
| **H 높음** | 저장 키/스키마·실사용자 데이터·권한/공개·고위험 정보·핵심 모델 | 기존 데이터 픽스처, 이전/읽기 호환, 실패·부분 변환·복구, 승인, 영향 범위 기능/안전 회귀 |

**MUST:** 가장 큰 위험을 기준으로 분류. 단순 CSS라도 초점 가림이나 텍스트 손실을 만들면 해당 접근성 검사 생략 금지. 변경이 누적되면 분류/리팩터링을 재평가한다.

### 6.3 기존 데이터·상태 호환성

- **MUST:** 이전 버전 저장 키·스키마·URL·북마크·작성 상태가 달라지면 **구버전 읽기 호환/명시적 마이그레이션/실패 복구·롤백**을 설계한다.
- **MUST:** 이전 구조를 대표하는 **실제 유형의 합성/허용된 픽스처**로 이전→새로고침→재방문→버전 전환을 검사한다. 새 버전에서 원래 데이터가 보이지 않는 것도 회귀다.
- **MUST:** 개인·민감정보를 퍼블릭 저장소·스크린샷·테스트 로그에 복제하지 않는다. 사용자 데이터 삭제/비가역 변환은 손실 위험과 승인 필요성을 선행 확인한다.
- **N/A:** 실제로 보존할 이전 데이터가 없는 초기 신규 프로젝트는 호환성 테스트가 비해당일 수 있지만 그 판단을 기록한다.

### 6.4 시험·보고 증거

| 검증 수준 | 결과로 주장할 수 있는 것 |
|---|---|
| 문서/코드 정적 검토 | 설계·구조·코드상의 부합 여부만 |
| 자동 테스트 | 실행 환경과 테스트 시나리오가 통과한 범위만 |
| 실제 브라우저/기기 시험 | 시험한 버전·뷰포트·기능·입력 환경만 |
| 실제 사용자 과업 시험 | 참여자·조건·과업의 관찰 범위만 |
| 임상/법률/접근성 전문가 검증 | 해당 전문 검토를 실제 받은 범위만 |

- **MUST:** 검증 상태는 `PASS / FAIL / NOT RUN / N/A`. 툴 호출·문서 작성·목업 생성·사용자 개인의 미감 승인을 실제 사용성/임상/접근성 검증 통과로 주장하지 않는다.
- **MUST:** 저장/발행/전송 성공 메시지는 실제 상태에 근거해야 한다. 의료진 검토→승인→환자 공개, 행정적 접수→수락→제공 등의 차이는 UI 모양이 아니라 상태 계약이다.
- **SHOULD:** 사용성 개선 주장이 필요하면 같은 작업·정보·기기·시간 조건에서 비교하고, **선택한 비교안이 실제로 화면에 적용됐는지** 확인한다. 미관·맥락 적합성·과업 성능·기술 정확성을 별도로 평가하며, 하나의 요소를 바꾸는 통제 실험과 여러 요소의 통합 평가를 구분한다.

## 7. 1분 리뷰 카드 — 해당하는 것만 확인

1. 목적/이용자가 첫 화면에서 이해하고 해야 할 행동이 분명한가? 히어로·감성 문구가 정말 필요한가?
2. 역할에 맞는 정보 밀도와 동시에 판단할 정보의 연결을 확보했는가?
3. 페이지 구조·탭/사이드바/표·입력 패턴을 목적과 플랫폼에 맞게 고른 이유가 있는가?
4. 폰트·한글 폴백·색·질감·모션이 소재에 맞고 익숙한 스타일을 반복하지 않는가?
5. 상태·출처·결측·검토/승인·작업 완료를 과장하거나 섞지 않았는가?
6. 키보드/터치/확대/반응형/스크린리더/움직임 감소 중 영향을 받는 항목을 검증했는가?
7. 기존 기능·URL·저장·데이터·보호할 강점이 보존됐는가?
8. 결과를 **미관 / 목적 적합성 / 사용성 / 코드·기능 검증**으로 나눠 설명했는가?
9. 무관한 참고자료와 테스트를 관성적으로 더 읽거나 실행해 비용만 늘리지는 않았는가?
10. PASS/FAIL/NOT RUN/N/A를 실제 근거와 함께 기록했는가?

- **1~3차 실험 보완 (2026-10-21):** 브랜드명 반복의 서체 관계·의도적 행 나눔, 소재·광원과 색의 관계, 탐색/선택 대비 상세 정보의 유효 폭, A/B 선택 상태의 실제 적용 검증을 **기존 SHOULD 문장 안에서만** 구체화했다. 사례 수치(1:2 비율, 38% 패널 폭 등)는 범용 의무 규칙으로 도입하지 않았다.
- **신규:** KRDS·Apple·Material 3의 선택적 레퍼런스 검색, 페이지/서비스/컴포넌트·플랫폼의 역할 분리. 공식 자료와 Figma 검색 이름의 증거 차이를 명확화.
- **신규:** 돌봄 플랫폼에서 관찰한 **역할별 정보 구조, 승인/공개/결측 상태 표현, 의료진/환자 작업 밀도의 차이**를 범용 가설과 안전 계약으로 분리.
- **강화:** MUL.·메뉴 룰렛 사례의 서로 다른 최적 레이아웃과 물성/모션/조작부의 목적 적합성, 부분 채택·기존 강점 보존.
- **유지·압축:** v1.2의 접근성, 타이포/색/모션, 위험도 L/M/H, 마이그레이션, 검증 증거, Rams/Braun. 상세 레퍼런스 표·단일 제품 예시·원본 비평은 링크로 이동.
- **미채택:** '모든 사이트에 Apple Liquid Glass', 'Material Rail이 웹의 유일한 정답', 'KRDS 1200px 전체 강제', '모든 의료 UI를 큰 카드로', '미검증 점수·AI 출력 자동 승인', '사용자 1인의 선호를 모든 사용자에게 강제'.
- **실험 관찰 (2026-10-21, 제한 범위):** 제품·콘텐츠·작업형 1차 A/B, 제품·콘텐츠형 2차 요소별 통제, 3차 통합 후보에 대한 사용자 1인의 시각적 선호 피드백을 확보했다. 실행 가능한 실험 HTML의 제한적 브라우저 기능·반응형 테스트 기록은 있지만, **독립 표본의 사용성 검증, 임상·의료진/환자 실증, 전체 접근성 인증, Material 3/Apple UI Kit 전체 variants·토큰 분석, 실제 토큰 비용 비교는 NOT RUN**. 사용자 선호를 보편적 성능 증거로 승격하지 않는다.
